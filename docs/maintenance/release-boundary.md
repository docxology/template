# Release boundary

The root package metadata declares the **4.0.1** candidate. Its dated changelog
entry records the frozen release intent; publication remains pending until the
acceptance and publication steps below pass. Final release-intent metadata must
be included in the exact revision submitted for release acceptance.
The prepared 4.0.0 candidate was not published; its notes are retained. Tagging and publication require the verified
acceptance and publication steps below. The earlier recorded root release is `3.8.0` /
`v3.8.0`; its original publication evidence is retained in
[subsystem history](subsystem-status-history.md). Historical standalone release
entries do not version the root package.

Before the next root release, reconcile these surfaces together:

1. Finish scoped implementation and independent review. Resolve the intended
   root version, each exemplar's own version/DOI metadata, dependency locks,
   release notes and final changelog wording before expensive acceptance.
2. Generate required publication outputs with their source-owned producers in
   provider dependency order, then freeze the final authored and generated bytes.
   Run every [Platform 4 required acceptance](platform-4-upgrade.md) lane against
   that exact revision. A later metadata, documentation or output change requires
   fresh evidence for the changed source; do not relabel an old receipt.
3. Supply a successful same-repository hosted run at that revision, its exact
   `platform-required-acceptance` artifact ID, and aggregate receipt SHA256.
   The bounded bundle contains only `output/readiness` evidence and the canonical
   `output/readiness/release-candidate/receipt.json` with `source_commit`.
4. Create the matching root tag only after acceptance passes, then manually
   dispatch the release workflow with that handoff. A root 4+ tag push alone is
   blocked. The dedicated [required acceptance workflow](../../.github/workflows/platform-required-acceptance.yml)
   produces the complete bundle only after every original requirement passes;
   partial CI receipts cannot authorize this step.
   Set `RELEASE_TAG` to the verified existing tag whose dereferenced commit
   is the accepted source SHA. Read the other values from one successful
   same-repository required-acceptance run, its exact uploaded
   `platform-required-acceptance` artifact ID, and the aggregate receipt's
   actual SHA256. Dispatch that complete handoff:

   ```bash
   gh workflow run release.yml --repo docxology/template --ref "$RELEASE_TAG" \
     -f tag="$RELEASE_TAG" \
     -f acceptance_run_id="$ACCEPTANCE_RUN_ID" \
     -f acceptance_artifact_id="$ACCEPTANCE_ARTIFACT_ID" \
     -f acceptance_receipt_sha256="$ACCEPTANCE_RECEIPT_SHA256"
   ```

   A matrix subset, ordinary CI result, later commit or unverified rebuilt wheel
   cannot substitute for this tuple.
5. Verify remote commit IDs, retrieved artifact hashes, publication identities,
   licenses, and working URLs, then refresh status and publication records.

Final changelog metadata describes the intended release. It cannot prove that a
tag, release or external publication exists. No release, tag, or external
publication is created by local verification.
See [`TO-DO.md`](../../TO-DO.md) for the remaining external release action and
[`docs/guides/publication-runbook.md`](../guides/publication-runbook.md) for
provider-specific publishing steps.

## Development checkpoint

Work on the 4.0.1 acceptance adapters may be committed on a development branch
while acceptance remains incomplete. Such a checkpoint preserves reviewed source
and focused regression checks; it is not a candidate acceptance receipt or a
release authorization. Unsupported source occurrences and missing native,
runtime, hosted, model or coverage evidence must remain blocked. Complete final
coverage, regenerated publication outputs, exact-SHA hosted acceptance and the
versioned release handoff are still required before publication.

## Inspect the current state

After explicitly preparing the locked environment, read existing local evidence:

```bash
uv run --no-sync --offline python -m infrastructure.reporting.release_readiness \
  --repo-root . --profile candidate --strict --format markdown \
  --readiness-receipt output/readiness/release-candidate/receipt.json
```

Use `--format json` for automation and `--profile released` for the additional
publication requirements. Strict exits are `0` pass, `1` failed, `75` blocked and
`2` unknown. The command launches no acceptance lanes and contacts no provider.
It checks the selected receipt against current local source/artifact bytes;
historical coverage and pipeline summaries remain informational.

A serialized receipt cannot create the live native reader operation required for
full admission. The installed original/reader workflow described in
[`installed-wheel-matrix.md`](../development/installed-wheel-matrix.md) supplies
that operation. A dashboard's blocked state does not replace that workflow or
authorize a tag. Root release, standalone publication and retrieved-asset
verification retain their own outcomes and evidence.

For quick feedback, use the focused checks for the changed subsystem first.
Complete the unchanged full gate inventory after the source/output freeze. Reuse
verified immutable dependency downloads; keep prepared runtimes separate from
accepted results. The CI document action uses `converter` only for ordinary
project cells that need converters, while infrastructure and full acceptance
retain native preparation. No gate, roster cell or coverage floor is omitted.
