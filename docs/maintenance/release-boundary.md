# Release boundary

The root package metadata declares the **4.5.0** candidate. Its changelog and
release notes record the release intent; publication remains pending until the
acceptance and publication steps below pass. The coordinated minor transaction
moves the root SDK, all 25 exemplar SDK requirements and their publication
platform bindings from the unpublished 4.4.1 preparation to 4.5.0 while retaining
exemplar own versions. Current release guidance is in [the 4.5.0 notes](../releases/v4.5.0.md).
The existing `v4.4.0` tag remains bound to its failed candidate and is not reused.
Final release-intent metadata must be included in the exact revision submitted
for release acceptance.

Earlier unpublished candidate notes remain historical records. The earlier
recorded root release is `3.8.0` / `v3.8.0`; its original publication evidence is
retained in [subsystem history](subsystem-status-history.md). Historical
standalone release entries do not version the root package.

Before the next root release, reconcile these surfaces together:

For the metadata preparation in step 1, use
`scripts/maintenance/coordinated_release.py --repo-root . plan --from-version <current> --to-version <next-patch>`.
Patch remains the default. For an explicit minor release, use
`... plan --from-version <current> --to-version <next-minor>.0 --release-kind minor`.
The major stays fixed, the minor increments exactly once and patch becomes zero;
major transitions and skipped minor versions are refused. The selected kind is
bound into the reviewed plan and reconstructed by check/apply. Both paths retain
all exemplar own versions, third-party locks and the same follow-up requirements;
metadata preparation does not authorize publication.
Review the canonical JSON and its SHA256, then run `check` and `apply` with that
exact plan, `--reviewed-sha256` and a fresh private `--journal` outside the checkout.
The transaction binds package/lock inputs and every canonical manuscript
publication binding. It preserves exemplar own versions and third-party lock
records, and retains exact compensating rollback bytes. Concurrent metadata
writers are unsupported; stale inputs or foreign rollback edits are refused.
Executable version guards and authored documentation must also be reconciled
before the final Source freeze. The command creates no tag, release or acceptance.

1. Finish scoped implementation and independent review. Resolve the intended
   root version, each exemplar's own version/DOI metadata, dependency locks,
   release notes and final changelog wording before expensive acceptance.
2. Generate required publication outputs with their source-owned producers in
   provider dependency order, then freeze the final authored and generated bytes.
   Run every [Platform 4 required acceptance](platform-4-upgrade.md) lane against
   that exact revision, including the 52-cell installed matrix (root plus the 25
   canonical exemplars on Python 3.14 and 3.15; a lock whose wheels cannot serve a
   target minor is satisfied from its nominated sdist, selected by
   `infrastructure.project.locked_dependency_export --minor <3.x>`, offline with
   `--no-build` and exact hashes). Then run the release publication gate over the
   same frozen bytes:

   ```bash
   uv run --no-sync --offline python scripts/audit/check_publication_outputs.py \
     --all-public --strict --jobs 4 --receipts output/readiness/publication-gate
   ```

   `--strict` is the release policy: `review_required` findings fail as well as
   blocking `error` findings, and one JSON receipt is written per audited project.
   A later metadata, documentation or output change requires fresh evidence for the
   changed source; do not relabel an old receipt.
3. Supply a successful same-repository hosted run at that revision, its exact
   `platform-required-acceptance` primary artifact ID, and logical aggregate
   receipt SHA256. The primary archive contains `candidate-index.json`; that
   index binds the exact source, canonical
   `output/readiness/release-candidate/receipt.json` and every ordered bounded
   `platform-required-acceptance-shard-NNNN` artifact. Retain the original API
   metadata and primary/shard archives before their declared expiry. The installed
   reader authenticates the complete indexed collection and its logical readiness
   bytes; a flat rebuilt archive or an index alone cannot replace that admission.
4. Create the matching root tag only after acceptance passes, then manually
   dispatch the release workflow with that handoff. A root 4+ tag push alone is
   blocked. The dedicated [required acceptance workflow](../../.github/workflows/platform-required-acceptance.yml)
   produces the complete bundle only after every original requirement passes;
   partial CI receipts cannot authorize this step.
   Set `RELEASE_TAG` to the verified existing tag whose dereferenced commit
   is the accepted source SHA. Read the other values from one successful
   same-repository required-acceptance run, its exact uploaded
   `platform-required-acceptance` primary artifact ID, and the logical aggregate receipt's
   actual SHA256. Dispatch that complete handoff:

   ```bash
   gh workflow run release.yml --repo docxology/template --ref "$RELEASE_TAG" \
     -f tag="$RELEASE_TAG" \
     -f acceptance_run_id="$ACCEPTANCE_RUN_ID" \
     -f acceptance_artifact_id="$ACCEPTANCE_ARTIFACT_ID" \
     -f acceptance_receipt_sha256="$ACCEPTANCE_RECEIPT_SHA256"
   ```

   A matrix subset, ordinary CI result, later commit or unverified rebuilt wheel
   cannot substitute for this tuple.
5. Verify remote commit IDs, retrieved artifact hashes, publication identities,
   licenses, and working URLs, then refresh status and publication records.

Final changelog metadata describes the intended release. It cannot prove that a
tag, release or external publication exists. No release, tag, or external
publication is created by local verification.
See [`TO-DO.md`](../../TO-DO.md) for the remaining external release action and
[`docs/guides/publication-runbook.md`](../guides/publication-runbook.md) for
provider-specific publishing steps.

## Development checkpoint

Work on the current acceptance adapters may be committed on a development branch
while acceptance remains incomplete. Such a checkpoint preserves reviewed source
and focused regression checks; it is not a candidate acceptance receipt or a
release authorization. Unsupported source occurrences and missing native,
runtime, hosted, model or coverage evidence must remain blocked. Complete final
coverage, regenerated publication outputs, exact-SHA hosted acceptance and the
versioned release handoff are still required before publication.

## Inspect the current state

After explicitly preparing the locked environment, read existing local evidence:

```bash
uv run --no-sync --offline python -m infrastructure.reporting.release_readiness \
  --repo-root . --profile candidate --strict --format markdown \
  --readiness-receipt output/readiness/release-candidate/receipt.json
```

Use `--format json` for automation and `--profile released` for the additional
publication requirements. Strict exits are `0` pass, `1` failed, `75` blocked and
`2` unknown. The command launches no acceptance lanes and contacts no provider.
It checks the selected receipt against current local source/artifact bytes;
historical coverage and pipeline summaries remain informational.

A serialized receipt cannot create the live native reader operation required for
full admission. The installed original/reader workflow described in
[`installed-wheel-matrix.md`](../development/installed-wheel-matrix.md) supplies
that operation. A dashboard's blocked state does not replace that workflow or
authorize a tag. Root release, standalone publication and retrieved-asset
verification retain their own outcomes and evidence.

For quick feedback, use the focused checks for the changed subsystem first.
Complete the unchanged full gate inventory after the source/output freeze. A
rendered-provenance receipt binds its exemplar's sources, configuration and the
tracked stage implementation under `infrastructure/` and `scripts/`, so editing
either tree invalidates it: re-run that exemplar's producers before the strict
gate instead of relabelling the receipt. Reuse
verified immutable dependency downloads; keep prepared runtimes separate from
accepted results. The CI document action uses `converter` only for ordinary
project cells that need converters, while infrastructure and full acceptance
retain native preparation. No gate, roster cell or coverage floor is omitted.
