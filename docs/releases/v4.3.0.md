# Research Project Template 4.3.0

This minor release prepares coordinated metadata for 4.3.0 and simplifies the
release-blocking CI and shard-selection surfaces. A version heading, local check or
generated publication file does not establish publication.
The exact-revision hosted acceptance and authenticated release handoff in the
[release boundary](../maintenance/release-boundary.md) remain required. The earlier
4.0.0, 4.0.1 and 4.0.2 preparations remain historical candidates. Public exemplars
keep their independent package and publication versions.

Date: 2026-10-28.

## Coordinated minor metadata preparation

The coordinated planner applied two reviewed minor transactions in sequence,
4.1.0 → 4.2.0 and 4.2.0 → 4.3.0, because it admits only the exact next minor
version. Each step was produced by `scripts/maintenance/coordinated_release.py`,
checked against the tree, and applied with its canonical plan SHA256 and a retained
private journal outside the checkout. 4.2.0 is an applied intermediate metadata step
and was never published; it is not a release candidate and owns no tag, note or
release record.

Both transactions move the root SDK version, the root and exemplar lock roots, and
every canonical exemplar `platform_version` compatibility and manuscript publication
binding together. Exemplar own versions, provider declarations and the declared
Python floor are unchanged. Four exemplars did re-resolve for cp315 wheels:
`torch 2.15.0`, `triton 3.9.0` and `cuda-bindings 13.4.4` in
`template_advanced_literature_review` and `template_literature_meta_analysis`, and
`hypothesis 6.170.13` in `template_autopoiesis` and `template_pools_rules_tools`;
every other third-party lock record is unchanged. `CITATION.cff` and the release-boundary note now declare
4.3.0; `infrastructure/_version.py` keeps its single metadata provider, which reads
the root package version rather than an independent constant.

## CI composition and shard selection

Duplicated outer-workflow steps became composite actions under `.github/actions/`:
`setup-actionlint`, `check-browser`, `run-public-lint`, `run-safety-scan` and
`run-tracked-guards`. `ci.yml` and `hardening.yml` now run one pinned
implementation of each step instead of two copies. In the lint job the public
Ruff/format/type gates and the safety scan launch concurrently behind a single step,
while the public-source scope producer and the tracked-tree guards stay serial and
blocking.

Every `hardening.yml` run keeps its own concurrency group with
`cancel-in-progress: false`, so a later dispatch or commit cannot cancel exact-commit
verification. The deep contract matrix runs at `max-parallel: 8` with one complete
module per lane; hosted measurements put the makespan floor at the slowest module, so
further lanes would not shorten the wall, and the 120-minute job budget is unchanged.

Functional shard balancing now uses the committed measured module durations in
[`ci-module-durations.json`](../../infrastructure/config/ci-module-durations.json)
instead of file byte size, with unmeasured modules falling back to a byte-size
estimate on the same scale. `scripts/gates/ci_module_durations_check.py` refuses stale
or invented manifest entries. The manifest is a measurement source only: it never
adds, removes or restricts a selected module. The routine family is measured from the
merged [functional-infra JUnit artifacts](https://github.com/docxology/template/actions/runs/40718577012)
of run 40718577012 (23 modules, 456 cases, 264.3 test-seconds): byte-size balancing
had produced 11.5 / 191.7 / 61.1 test-seconds per shard, and weighting puts the single
162.8-second `tests/infra_tests/core/test_pipeline.py` module in its own lane for a
162.8-second makespan. That module now bounds the smoke lane; shortening it is the
next measured step, not a shard-selection change.
`scripts/gates/local_gate.py` provides one offline local entry point for the commands
the hosted jobs run.

The release publication audit is modular: `scripts/audit/check_publication_outputs.py`
audits a chosen roster (`--project`, `--all-public`, `--changed`), takes a
`--shard INDEX/COUNT` slice, audits projects in parallel (`--jobs`) and writes one
receipt per project (`--receipts`). Findings split into blocking `error` and
`review_required`; `--strict` is the release policy that fails on both. `release.yml`
runs `--all-public --strict --jobs 4` over all 25 exemplars and uploads the receipts,
while `hardening.yml` keeps the source-only
`publication-audit --all-public --strict --format json`, because rendered and native
lanes belong to required acceptance. `local_gate.py` gains a `publication` stage that
audits only changed projects.

Build and verification cost drops on the paths that used to dominate:
documentation-only changes no longer select the 25-exemplar functional matrix or
the contract roster (`infrastructure.core.testing.ci_selection.documentation_only`;
they run the documentation contracts instead), the automatic functional shards now
cap at 12 modules (`AUTOMATIC_SHARD_MAX_MODULES`) so a long module cannot stretch a
shard, the rendered-provenance stage fingerprint hashes tracked `.py` files rather
than prose, and `scripts/maintenance/refresh_rendered_provenance.py --jobs` refreshes
exemplars in worker processes (25 exemplars in about five minutes instead of eight).

## Retained contracts

`build_pytest_marker_expression` keeps its keyword defaults as the single declared
repository selection and now exposes `repository_marker_expression()` for the
`addopts` binding. Multi-exception `except` clauses stay parenthesized, and the Ruff
`target-version` is now `py313` in the root and both exemplar configurations that
declared one: `py314` made `ruff format` rewrite `except (A, B):` into the PEP 758
form and reflowed 169 files that were otherwise untouched, so the format gate and the
source disagreed. The runtime floor remains `requires-python >=3.14`; only the
formatter's syntax target moved, which keeps the source parseable by pre-3.14 parsers.
Standalone-mirror source/provider admission and committed-publication parity moved
into `_standalone_mirror_source` and `_standalone_mirror_verify`, with the export
surface, custody checks and receipt parity unchanged.

## Upgrade notes for projects

Projects declare the SDK they build against through
`[tool.template].platform_version` and the `research-project-template==<version>`
requirement. Both now read 4.3.0, and each project's `manuscript/config.yaml`
publication binding declares `platform_version: "4.3.0"`. A project that pins an
earlier platform version must re-pin to 4.3.0 before it is validated against this
source; a project's own package version, publication version and DOI are independent
of this number and are not changed by this preparation. Third-party requirements are
untouched apart from the cp315 refresh named above: projects consuming
`torch`/`triton`/`cuda-bindings`/`hypothesis` need `uv sync --locked` to pick up
those lock records, and every other project needs no re-resolution for the metadata
change.

## Version identity across the root and 25 standalone repositories

Each exemplar publishes to its own repository, so two numbers must stay
distinguishable: the *intended* version in `pyproject.toml` and the *last
published* version recorded in `CITATION.cff`, `.zenodo.json`, `codemeta.json` and
`manuscript/config.yaml` `publication.last_published_version`. Sidecars keep
describing the last real publication while the package version advances; the
generated publication matrix reports both.

`scripts/audit/check_release_versions.py` now enforces that agreement for the root
and all 25 exemplars: `intended_version` equals `pyproject.toml`, sidecars equal
`last_published_version`, `version_doi` exists exactly when a publication exists,
`release_status` matches the comparison, `platform_version` follows the root, and
the repository is declared as `owner/name`. For the root it also requires the
changelog heading, `docs/releases/v<version>.md`, the release artwork
(`template-v<version>-overview.svg`/`.png`, which `release.yml` uploads and
`root_release_artifacts` indexes), and — on a tag push — that the tag is exactly
`v<version>`. The same run also makes `publication_records.py --check` fail on sidecar
drift it previously computed and discarded.

## Forking and project-owned configuration

Every canonical exemplar now declares the SDK it builds against, including the
five that previously declared only `platform_version`
(`data_descriptor`, `experiment_tree`, `newspaper`, `redacted_report`,
`storybook`): each carries the `4.3.0` pin plus a `[tool.uv.sources]` entry and a
lock whose diff is additions only.

Project-owned `manuscript/config.yaml` blocks are declared in the project rather
than named in Layer 1:

```toml
[tool.template]
config_keys = ["madlib"]   # extra top-level blocks this project owns
```

`infrastructure.core.project_pyproject` reads that declaration and
`validate_config_keys` accepts the keys for that project only; a malformed
declaration is reported. `scripts/audit/check_exemplar_configs.py` enforces this,
the platform pin and its declared source, `platform_version` agreement, and
consistency with the generated publication copy, in the `ci.yml` lint job and
`local_gate.py gates`.

Forking is now a documented, self-describing operation: `copy_exemplar.py`
accepts `--sdk-source path:|url:|version-only` and
`--author-name/--author-email`, which rewrite the fork's own identity and drop the
source DOI, ORCID, repository URL and release date. See
[the fork section](../../README.md#forking-an-exemplar).

## Verification and publication state

This note records a metadata preparation, not a publication. Tagging, the GitHub
release, the Zenodo record and any hosted acceptance evidence are separate
authorized steps that must run against the exact final revision. The applied plans,
their SHA256s and the retained journals are the prepared-artifact evidence for this
step; they do not substitute for the plan's declared follow-up obligations: locked
offline metadata checks, source-bound coverage and publication validation, the 52-cell
installed matrix (root plus 25 exemplars on Python 3.14 and 3.15, nominating a lock's
exact sdist via `infrastructure.project.locked_dependency_export --minor` whenever its
wheels cannot serve the target minor), a fresh final source census and policy
admission, the exact-main obligations and the independent installed-release handoff.
A rendered-provenance receipt binds its exemplar's sources and configuration plus the
tracked implementation under `infrastructure/` and `scripts/`, so edits there require
re-running the exemplar producers before the strict gate.

The canonical public output ceiling is `PUBLIC_TEMPLATE_OUTPUT_MAX_TOTAL_BYTES = 224 MiB`
in `infrastructure/project/git_guards.py` — 5% headroom over the 218,059,616 bytes the
regenerated 25-exemplar output set measures (previously 0.3%) — still enforced by
`scripts/audit/check_tracked_generated_artifacts.py`.

The exemplar sources changed in this preparation (platform pin, `platform_version`,
and version guards), so `scripts/docgen/counts.py --check` reports stale coverage
provenance for the changed measurement inputs. Refreshing that record without a fresh
measurement would launder old percentages into a new source revision, so the
provenance stays stale until each affected exemplar's coverage gate runs again. That
is a required acceptance step, not a formatting fix.

An attempted re-measurement from this development host could not start: every one of
the 25 exemplars returned the same pre-startup refusal, `bounded-run guardian refused
source custody` (exit 75), before pytest ran, and the same refusal reproduces on the
unmodified base tree. The measurement pipeline is therefore untested here rather than
green; it must run on a host where the bounded-run guardian can start (the hosted
runners do). Each exemplar's own suite is green separately: 24 suites pass directly,
and Active Inference's complete own suite passes with its documented
`TEMPLATE_ACTIVE_INFERENCE_ALLOW_GATE_REBUILD=1` local refresh (its committed gate
snapshot is the remaining refresh item, tracked as `P4-EXEMPLAR-GATE-SNAPSHOT-1`).

Current generated facts belong in [COUNTS.md](../_generated/COUNTS.md), the
[public roster](../_generated/active_projects.md) and their retained provenance.
Root status is recorded in [STATUS.md](../../STATUS.md). Publication is established
by the authenticated GitHub release and its exact-source workflow evidence.
