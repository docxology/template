# Research Project Template 4.4.0

## Coordinated minor metadata preparation

4.4.0 is the published successor to the 4.3.0 candidate. It carries the
publication-evidence and CI work that 4.3.0 prepared, plus the verification
speed-ups and documentation corrections that the 4.3.0 release rehearsal
surfaced. The root package, `infrastructure/_version.py` and each canonical
public exemplar's `[tool.template].platform_version` declare 4.4.0; exemplar
package versions remain independent.

## Publication gate

The release publication audit is the modular
`scripts/audit/check_publication_outputs.py`: it selects a roster
(`--project`, `--all-public`, `--changed`), slices it with `--shard INDEX/COUNT`,
audits each project in parallel (`--jobs`), separates blocking `error` findings
from `review_required` ones, and writes one JSON receipt per audited project
(`--receipts`). `--strict` is the release policy and fails on both severities.

`release.yml` runs `--all-public --strict --jobs 4` over all 25 exemplars,
retains the receipts as an artifact, and only then requires the root 4+ hosted
acceptance handoff. `hardening.yml` keeps the source-only
`publication-audit --all-public --strict --format json` lane because rendered and
native layers belong to required acceptance. `local_gate.py` gains a
`publication` stage that audits only changed projects.

## Verification cost

Four changes cut the verification cycle without weakening any gate:

- Documentation-only changes no longer select the exemplar matrix or the
  contract roster. `infrastructure.core.testing.ci_selection.documentation_only`
  recognises prose and documentation artwork, so those changes run the
  documentation contracts and nothing else.
- Automatic functional shards cap at twelve modules
  (`ci_infra.AUTOMATIC_SHARD_MAX_MODULES`), so one long module can no longer
  stretch a shard; the measured-duration manifest still drives dispatch order and
  balance.
- The rendered-provenance stage fingerprint hashes the tracked `.py` stage
  implementation, not prose, so editing an `AGENTS.md` no longer invalidates all
  25 proofs while editing a stage module still does.
- `scripts/maintenance/refresh_rendered_provenance.py --jobs` refreshes exemplars
  in worker processes and accepts `--jobs 1` for the strict serial path.

## Installed matrix and dependency resolution

The installed matrix is 52 cells: the root plus the 25 canonical exemplars on
Python 3.14 and 3.15. A locked release whose wheels cannot serve a target minor
is nominated as its exact locked sdist
(`infrastructure.project.locked_dependency_export --minor`), built once into the
warm cache and still installed offline with `--no-build` and exact hashes.
PyYAML 6.0.3 publishes cp314 wheels only, and the cell's minor is now forwarded
from the cell runner, so those cells resolve instead of failing closed.

Four exemplars re-resolved for cp315 wheels — `torch 2.15.0`, `triton 3.9.0` and
`cuda-bindings 13.4.4` in `template_advanced_literature_review` and
`template_literature_meta_analysis`, and `hypothesis 6.170.13` in
`template_autopoiesis` and `template_pools_rules_tools`. `wordcloud` is
marker-capped to `python_version < "3.15"`; the meta-analysis exemplar renders a
deterministic golden-angle spiral term cloud when the extension is unavailable.

## Retained contracts

- Rendered-provenance receipts bind each exemplar's sources and configuration
  plus the tracked `.py` stage implementation under `infrastructure/` and
  `scripts/`.
- Canonical public output bytes stay inside
  `PUBLIC_TEMPLATE_OUTPUT_MAX_TOTAL_BYTES = 224 MiB`
  (`infrastructure/project/git_guards.py`), enforced by
  `scripts/audit/check_tracked_generated_artifacts.py`.
- Root 4+ publication requires a successful `platform-required-acceptance.yml`
  run on the exact tag revision, its `platform-required-acceptance` artifact ID
  and the SHA-256 of `output/readiness/release-candidate/receipt.json`.
- Every canonical public exemplar keeps its forkable surface and its
  `[tool.template]` contract (`platform_version`, `tested_python_versions`,
  `required_unpaid_capabilities`).

## Upgrade notes for projects

Root and exemplar `pyproject.toml` pins move from `research-project-template==4.3.0`
to `==4.4.0`; each exemplar's `uv.lock` is refreshed accordingly. Projects that
declare `torch`, `triton`, `cuda-bindings` or `hypothesis` must re-resolve to pick
up the cp315-capable releases. Nothing else changes for project-owned content.

## Verification and publication state

The strict all-public gate passes for all 25 exemplars with zero blocking and
zero `review_required` findings after every producer was re-run. Documentation
linters, module-reference and module-doc-coverage gates, exemplar-configuration
and release-version gates, `ruff` and `mypy` all pass. Publication requires the
hosted required-acceptance handoff described above; until that handoff completes,
4.4.0 remains an intended, unpublished version.
